# 이미지 제작·캡처·묶음 전달

완성 원고를 제공할 때마다 같은 답변에 실제 도구로 만든 썸네일과 원문 캡처 이미지를 함께 제공한다. 사용자가 원고만 요청한 경우는 예외다. 모바일에서 여러 장을 한 번에 저장할 수 있는 이미지 묶음을 우선한다. 블라인드는 확인한 원문 링크를 전달하고 사용자가 캡처한다.

기준 절차:
https://github.com/yunsj0121/naver-blog-seo-writer/blob/6df8430aa65715a5866ea718660e46031ff80799/docs/pipeline-redev.md#L113

## 제작과 전달을 구분한다

`economicissue build/draft`는 원고와 이미지 입력용 레이아웃·실제 캡처를 준비한다. Python CLI가 ChatGPT의 이미지 생성 또는 첨부 도구를 직접 실행했다고 표시하지 않는다.

`delivery.json`에는 각 파일의 실제 종류, 해시, 필요한 생성 결과 수, 실제 캡처 첨부 수, 묶음 순서가 기록된다. 생성 입력은 `generation_input`, 원문은 `source_capture`로 구분한다. 문서 생성만으로 완료 상태로 바꾸지 않는다.

## 실제 제작 이미지

1. 작업 에이전트가 `image-generation.json`과 확정 원고를 읽고 입력 PNG를 확인한다. `input_path`는 최종 묶음 폴더 기준 상대 경로이므로 도구에 넘길 때 절대 경로로 해석한다. 저장된 해시도 확인한다.
2. 각 작업은 실제 `image_gen.imagegen`으로 실행한다. `referenced_image_paths`에는 해당 입력 PNG 한 장을 넣는다. 썸네일은 1:1, 큰 글씨이며 승인된 문구·숫자·단위를 유지한다.
3. 실제 반환 객체를 현재 세션의 저장소에 보존한다. 파일 경로나 `view_image` 데이터 URL을 반환 객체라고 꾸미지 않는다. 생성 결과의 한글·수치·비율을 직접 확인한다.
4. 같은 응답에서 결과들을 입력 순서대로 `generatedImage(result)`에 전달한다. 같은 글의 결과 사이에 다른 미리보기나 파일 링크를 끼우지 않는다.
5. 실패하면 성공 결과를 보존하고 실패한 작업만 다시 실행한다. 전체 이미지를 다시 생성하지 않는다. 반환 형식에 없는 `content` 등의 필드를 가정하지 않는다.

`generatedImage`는 작업 에이전트 실행 환경의 출력 함수이며 Python 함수가 아니다. 아래 결과들은 반드시 실제 이미지 생성 도구의 반환 객체여야 한다.

```javascript
for (const result of orderedActualImageGenResults) {
  generatedImage(result)
}
```

## 실제 원문 캡처

브라우저에서 실제 원문·영역을 확인해 캡처한다. `raw-captures/`에는 밑줄 전 원본을, `marked-captures/`에는 밑줄 후 원본을 보존한다. 전달용 사본은 내용이 잘리지 않게 흰 여백으로 1080×1080 정사각형에 맞춘다. 출처·영역·파일 해시를 기록하며, 캡처 실패를 가짜 화면으로 메우지 않는다. 실패한 원문은 코드블록 밖에 바로가기를 제공한다.

캡처는 이미지 생성 작업에 넣지 않는다. 해시로 확인한 실제 PNG를 지원되는 이미지 첨부 기능으로 별도 묶음에 직접 첨부한다. `generatedImage`에 캡처 파일이나 미리보기 URL을 넣지 않는다. 미리보기 이미지가 모델에게 보이는 것과 사용자에게 실제 첨부되는 것은 다르다.

## 완료 판정

이미지 생성·캡처 성공, 이미지 검수, 사용자 첨부, 모바일 묶음 저장은 서로 다른 단계다. 실제 네이티브 이미지 묶음과 일괄 저장이 확인되지 않으면 pending 상태를 유지한다. 사용자가 여러 장을 개별 저장해야 한다고 알려주면 미완료다.

네이티브 묶음을 지원하지 않으면 검증된 실제 이미지를 채팅에서 볼 수 있는 현재 환경의 표시 방식으로 제공한다. 마크다운 이미지 표시와 파일 링크는 그 방식으로 설명하며 네이티브 첨부나 모바일 일괄 저장의 확인으로 취급하지 않는다. 이미지가 누락되거나 표시 가능 여부를 확인할 수 없으면 해당 이미지와 사유를 명시한다. HTML·ZIP 등 보조 내보내기는 사용자가 요청한 경우 제공한다.

### 답변 직전 검사

1. 새 제작과 재전달 모두 `economicissue delivery-check --bundle <결과 폴더>`를 실행한다. 원고에 필요한 수와 순서, 역할, PNG 디코딩, 파일 해시를 확인한다. `file_status=invalid`인 파일은 표시용 경로나 첨부 입력으로도 넘기지 않는다. 기존에 검증된 후보를 보존하고 실패 파일만 복구한 후 재검사한다.
2. 현재 세션의 도구 설명을 확인한다. 제작 이미지는 실제 image_gen 결과를 반환한다. 원문 PNG는 현재 세션에서 지원하는 이미지 첨부 기능으로 전달한다. 네이티브 첨부 도구가 없으면 `unsupported`로 기록하고 검증된 이미지를 지원되는 채팅 표시 방식으로 제공한다. 도구 미리보기 및 파일 업로드 서비스는 채팅의 네이티브 묶음 첨부와 별개다.
3. 실제 호출 뒤 아래 형식으로 관찰 기록을 작성하고 `economicissue delivery-check --bundle <결과 폴더> --delivery-observations <기록.json>`을 실행한다. `tool`은 실제 실행한 도구, `result_ref`는 성공 결과에 실제로 포함된 식별자다. 사용자 향 이미지 반환이 확인된 제작 이미지에는 `image_gen_result_return`, 원문에는 `native_png_attachment`를 쓴다. `sha256`은 이번에 검수하고 처리한 전달 목록 항목의 해시다. 생성 성공만 반환하거나 이미지 출력 함수가 첨부 결과를 반환하지 않는 환경에서는 첨부 성공 항목을 만들지 않는다. 이 기록은 에이전트의 관찰이며 CLI는 채팅 서비스에 직접 조회하지 않는다.

```json
{
  "02_body.png": {"content_reviewed": true, "attachment": "unsupported"},
  "03_body.png": {
    "content_reviewed": true,
    "attachment": "success",
    "receipt": {
      "method": "native_png_attachment",
      "sha256": "<전달 목록의 실제 해시>",
      "tool": "<실제 첨부 도구>",
      "result_ref": "<실제 성공 결과 식별자>"
    }
  }
}
```

4. 최종 답변은 검사 결과의 `reported_attached`와 `missing_attachments`를 기준으로 작성한다. 일부 성공이면 “3장 중 2장 첨부”와 누락 파일 및 사유를 적는다. `capture_unavailable`은 원문 캡처 실패이며 생성 대체 대상에서 제외한다. 사용자 화면의 표시와 일괄 저장은 모바일에서 별도로 확인한 경우만 확인됐다고 안내한다. 사용자가 별도로 허용한 대체 방식은 그 방식의 이름으로 안내한다.
